# Speckit Workflow - Expanded Documentation

## Overview

Speckit is a feature-driven development workflow system that guides teams from natural language feature descriptions through specification, planning, task breakdown, and implementation. It enforces a disciplined approach to software development with clear phase gates and quality checks.

## Complete Workflow Diagram

```
User Request
    ↓
/speckit.constitution (Optional - Project Governance)
    ↓
/speckit.specify (Feature Specification)
    ↓
/speckit.clarify (Requirements Clarification - Optional but Recommended)
    ↓
/speckit.plan (Technical Planning)
    ↓
/speckit.tasks (Task Breakdown)
    ↓
/speckit.analyze (Cross-Artifact Consistency Check - Optional)
    ↓
/speckit.checklist (Quality Checklists - Optional, Multiple)
    ↓
/speckit.implement (Implementation Execution)
    ↓
/speckit.taskstoissues (Convert Tasks to GitHub Issues - Optional)
```

## Git Extension Workflow (Parallel)

```
/speckit.git.initialize (Project Setup - One Time)
    ↓
/speckit.git.feature (Feature Branch Creation - Before Specify)
    ↓
/speckit.git.validate (Branch Validation - Anytime)
    ↓
/speckit.git.commit (Auto-Commit - After Commands)
    ↓
/speckit.git.remote (Remote Detection - For GitHub Integration)
```

## Detailed Phase Descriptions

### Phase 0: Project Setup (Optional)

**Command**: `/speckit.constitution`

**Purpose**: Establish or update project governance principles that guide all subsequent development decisions.

**Inputs**:
- User-provided principles or governance requirements
- Existing `.specify/memory/constitution.md` (if present)

**Outputs**:
- Updated constitution file with versioned principles
- Sync Impact Report documenting changes
- Propagation to dependent templates (plan, spec, tasks)

**Key Activities**:
1. Load existing constitution template
2. Collect/derive principle values from user input or repo context
3. Fill all placeholder tokens with concrete values
4. Version management (semantic versioning for governance changes)
5. Consistency propagation across all dependent templates
6. Validation (no unexplained brackets, valid dates, testable principles)

**Quality Gates**:
- All placeholder tokens resolved
- Version incremented per semantic rules
- Principles are declarative and testable
- Templates synchronized with updated principles

---

### Phase 1: Feature Specification

**Command**: `/speckit.specify`

**Purpose**: Transform a natural language feature description into a structured, testable specification document.

**Inputs**:
- Natural language feature description (user prompt)
- Spec template from `.specify/templates/spec-template.md`
- Optional: Git branch from `before_specify` hook

**Outputs**:
- `specs/<prefix>-<short-name>/spec.md` - Complete feature specification
- `specs/<prefix>-<short-name>/checklists/requirements.md` - Quality checklist
- `.specify/feature.json` - Feature directory mapping

**Key Activities**:
1. **Generate Short Name**: Extract 2-4 word identifier (e.g., "user-auth", "oauth2-api-integration")
2. **Branch Creation** (via hook): Create/switch to feature branch if git extension configured
3. **Directory Creation**: Create spec directory under `specs/` with numbering prefix
4. **Parse Description**: Extract actors, actions, data, constraints
5. **Fill Specification**:
   - User scenarios and testing flows
   - Functional requirements (testable, unambiguous)
   - Success criteria (measurable, technology-agnostic)
   - Key entities (if data involved)
   - Assumptions and dependencies
6. **Quality Validation**:
   - Run against quality checklist
   - Resolve [NEEDS CLARIFICATION] markers (max 3)
   - Present clarification options to user when needed
   - Iterate until all checklist items pass (max 3 iterations)

**Clarification Handling**:
- Maximum 3 [NEEDS CLARIFICATION] markers allowed
- Prioritized by: scope > security/privacy > UX > technical details
- Presented as multiple-choice tables with recommended options
- User selects or provides custom answers
- Spec updated with resolved answers

**Quality Gates**:
- No implementation details in spec
- All requirements testable and unambiguous
- Success criteria measurable and technology-agnostic
- User scenarios cover primary flows
- Edge cases identified
- No remaining [NEEDS CLARIFICATION] markers

**Extension Hooks**:
- `before_specify`: Branch creation, pre-specification setup
- `after_specify`: Post-specification automation (commits, notifications)

---

### Phase 2: Requirements Clarification (Optional but Recommended)

**Command**: `/speckit.clarify`

**Purpose**: Identify and resolve ambiguity in the specification before technical planning begins.

**Inputs**:
- Existing `spec.md` from Phase 1
- Taxonomy of ambiguity categories

**Outputs**:
- Updated `spec.md` with clarifications integrated
- Clarifications session log with Q&A history

**Key Activities**:
1. **Load Spec**: Read existing specification file
2. **Coverage Scan**: Analyze spec against ambiguity taxonomy:
   - Functional Scope & Behavior
   - Domain & Data Model
   - Interaction & UX Flow
   - Non-Functional Quality Attributes
   - Integration & External Dependencies
   - Edge Cases & Failure Handling
   - Constraints & Tradeoffs
   - Terminology & Consistency
   - Completion Signals
   - Misc / Placeholders
3. **Generate Questions**: Up to 5 prioritized clarification questions
   - Each answerable via multiple-choice (2-5 options) or short answer (≤5 words)
   - Only questions that materially impact architecture, data modeling, or test design
   - Recommended options provided with reasoning
4. **Sequential Questioning**:
   - One question at a time
   - User accepts recommendation or provides custom answer
   - Immediate integration into spec after each answer
   - Spec saved after each integration (atomic overwrite)
5. **Validation**: After each write and final pass
   - No lingering placeholders
   - No contradictory statements
   - Markdown structure valid
   - Terminology consistent

**Question Constraints**:
- Maximum 5 total questions
- Each must impact architecture, data modeling, task decomposition, test design, UX, or compliance
- Category balance: cover highest impact unresolved categories first
- Exclude already-answered, trivial, or plan-level details

**Quality Gates**:
- All accepted answers integrated into spec
- No contradictory statements remain
- Total questions asked ≤ 5
- Spec file saved with clarifications session log

**Extension Hooks**:
- `before_clarify`: Pre-clarification setup
- `after_clarify`: Post-clarification automation

### Phase 3: Technical Planning

**Command**: `/speckit.plan`

**Purpose**: Create a detailed technical implementation plan from the specification.

**Inputs**:
- `spec.md` from Phase 1/2
- Constitution from Phase 0 (if present)
- Plan template from `.specify/templates/plan-template.md`

**Outputs**:
- `specs/<prefix>-<short-name>/plan.md` - Technical implementation plan
- `specs/<prefix>-<short-name>/research.md` - Research findings and decisions
- `specs/<prefix>-<short-name>/data-model.md` - Entity definitions and relationships
- `specs/<prefix>-<short-name>/contracts/` - Interface contracts (if applicable)
- `specs/<prefix>-<short-name>/quickstart.md` - Integration scenarios
- Updated agent context in `.kilocode/rules/specify-rules.md`

**Key Activities**:

**Phase 0: Outline & Research**
1. Extract unknowns from Technical Context section
2. Generate research tasks for each unknown
3. Research best practices for technology choices
4. Consolidate findings in `research.md`:
   - Decision: what was chosen
   - Rationale: why chosen
   - Alternatives considered: what else evaluated
5. Resolve all NEEDS CLARIFICATION markers

**Phase 1: Design & Contracts**
1. Extract entities from feature spec → `data-model.md`:
   - Entity names, fields, relationships
   - Validation rules from requirements
   - State transitions if applicable
2. Define interface contracts → `contracts/`:
   - Identify external interfaces (APIs, commands, endpoints, UI contracts)
   - Document contracts in appropriate format for project type
   - Skip if project is purely internal
3. Update agent context:
   - Update plan reference in `.kilocode/rules/specify-rules.md`

**Constitution Check**:
- Evaluate plan against constitution principles
- ERROR if violations unjustified
- Re-evaluate post-design

**Quality Gates**:
- All NEEDS CLARIFICATION resolved in research.md
- Data model complete with entities, fields, relationships
- Contracts defined for all external interfaces
- Constitution compliance verified
- Gate failures result in ERROR

**Extension Hooks**:
- `before_plan`: Pre-planning setup
- `after_plan`: Post-planning automation

### Phase 4: Task Breakdown

**Command**: `/speckit.tasks`

**Purpose**: Generate an actionable, dependency-ordered task list from the technical plan.

**Inputs**:
- `plan.md` from Phase 3
- `spec.md` from Phase 1/2
- Optional: `data-model.md`, `contracts/`, `research.md`, `quickstart.md`

**Outputs**:
- `specs/<prefix>-<short-name>/tasks.md` - Complete task breakdown

**Key Activities**:
1. **Load Design Documents**:
   - Required: plan.md (tech stack, libraries, structure), spec.md (user stories with priorities)
   - Optional: data-model.md, contracts/, research.md, quickstart.md
2. **Extract Context**:
   - Tech stack and libraries from plan.md
   - User stories with priorities (P1, P2, P3...) from spec.md
   - Entities mapped to user stories from data-model.md
   - Interface contracts mapped to user stories from contracts/
   - Decisions extracted for setup tasks from research.md
3. **Generate Tasks** (organized by user story):
   - **Phase 1**: Setup (project initialization)
   - **Phase 2**: Foundational (blocking prerequisites for all user stories)
   - **Phase 3+**: User Stories in priority order (P1, P2, P3...)
     - Within each story: Tests (if requested) → Models → Services → Endpoints → Integration
     - Each phase is a complete, independently testable increment
   - **Final Phase**: Polish & Cross-Cutting Concerns
4. **Task Format** (strict checklist format):
   ```
   - [ ] [TaskID] [P?] [Story?] Description with file path
   ```
   - TaskID: Sequential number (T001, T002, T003...)
   - [P]: Parallelizable marker (only if task is parallelizable)
   - [Story]: User story label ([US1], [US2], etc.) - only for user story phases
   - Description: Clear action with exact file path
5. **Generate Dependency Graph**:
   - User story completion order
   - Parallel execution examples per user story
6. **Validation**:
   - Each user story has all needed tasks
   - Each story independently testable
   - All tasks follow strict checklist format

**Task Organization Rules**:
- From User Stories: PRIMARY organization (each story gets own phase)
- From Contracts: Map to serving user story
- From Data Model: Map entity to needing user story(ies)
- From Setup/Infrastructure: Shared → Setup, Story-specific → story phase

**Quality Gates**:
- All tasks follow strict checklist format
- Each user story phase independently testable
- Dependencies clearly marked
- Parallel opportunities identified
- MVP scope suggested (typically User Story 1)

**Extension Hooks**:
- `before_tasks`: Pre-task generation setup
- `after_tasks`: Post-task generation automation

### Phase 5: Cross-Artifact Analysis (Optional)

**Command**: `/speckit.analyze`

**Purpose**: Perform non-destructive consistency and quality analysis across spec.md, plan.md, and tasks.md.

**Inputs**:
- `spec.md` from Phase 1/2
- `plan.md` from Phase 3
- `tasks.md` from Phase 4
- Constitution from Phase 0 (if present)

**Outputs**:
- Analysis report (markdown, no file writes)
- Coverage summary table
- Next actions recommendations
- Optional remediation plan (user must approve)

**Key Activities**:
1. **Initialize**: Verify all required files exist
2. **Load Artifacts** (minimal necessary context):
   - From spec.md: Overview, Functional Requirements, Success Criteria, User Stories, Edge Cases
   - From plan.md: Architecture, Data Model, Phases, Constraints
   - From tasks.md: Task IDs, Descriptions, Phase Grouping, Parallel Markers, File Paths
   - From constitution: Principles and MUST/SHOULD statements
3. **Build Semantic Models**:
   - Requirements inventory (FR-###, SC-###)
   - User story/action inventory
   - Task coverage mapping
   - Constitution rule set
4. **Detection Passes**:
   - **Duplication**: Near-duplicate requirements
   - **Ambiguity**: Vague adjectives, unresolved placeholders
   - **Underspecification**: Missing objects, missing acceptance criteria
   - **Constitution Alignment**: MUST principle violations
   - **Coverage Gaps**: Requirements with zero tasks, tasks with no requirement
   - **Inconsistency**: Terminology drift, data entity mismatches, ordering contradictions
5. **Severity Assignment**:
   - CRITICAL: Constitution MUST violations, missing core artifacts, zero-coverage blocking requirements
   - HIGH: Duplicate/conflicting requirements, ambiguous security/performance attributes
   - MEDIUM: Terminology drift, missing non-functional coverage, underspecified edge cases
   - LOW: Style/wording improvements, minor redundancy
6. **Produce Report**:
   - Findings table (max 50 rows, overflow summarized)
   - Coverage summary table
   - Constitution alignment issues
   - Unmapped tasks
   - Metrics (total requirements, tasks, coverage %, ambiguity count, etc.)
7. **Next Actions**:
   - CRITICAL issues: Recommend resolving before `/speckit.implement`
   - LOW/MEDIUM only: User may proceed with improvement suggestions
   - Command suggestions for remediation
8. **Offer Remediation**: Ask user if they want concrete remediation edits (not automatic)

**Operating Principles**:
- STRICTLY READ-ONLY (no file modifications)
- Constitution authority is non-negotiable
- Token-efficient (limit 50 findings, summarize overflow)
- Deterministic results (rerunning produces consistent IDs)

**Quality Gates**:
- All required files present
- Analysis covers all detection categories
- Severity properly assigned
- Report includes actionable next steps

**Extension Hooks**:
- `before_analyze`: Pre-analysis setup
- `after_analyze`: Post-analysis automation

### Phase 6: Quality Checklists (Optional, Multiple)

**Command**: `/speckit.checklist`

**Purpose**: Generate custom checklists that validate requirements quality ("Unit Tests for English").

**Inputs**:
- User requirement for checklist domain (e.g., "security", "ux", "api")
- `spec.md`, `plan.md`, `tasks.md` for context

**Outputs**:
- `specs/<prefix>-<short-name>/checklists/<domain>.md` - Domain-specific checklist

**Key Activities**:
1. **Clarify Intent**: Up to 3 contextual questions (max 5 total):
   - Scope refinement
   - Risk prioritization
   - Depth calibration
   - Audience framing
   - Boundary exclusion
   - Scenario class gaps
2. **Load Feature Context**:
   - spec.md: Requirements and scope
   - plan.md: Technical details (if exists)
   - tasks.md: Implementation tasks (if exists)
3. **Generate Checklist** ("Unit Tests for Requirements"):
   - **NOT** testing implementation behavior
   - **FOR** testing requirements quality:
     - Completeness: Are all necessary requirements present?
     - Clarity: Are requirements unambiguous and specific?
     - Consistency: Do requirements align with each other?
     - Measurability: Can requirements be objectively verified?
     - Coverage: Are all scenarios/edge cases addressed?
4. **Category Structure**:
   - Requirement Completeness
   - Requirement Clarity
   - Requirement Consistency
   - Acceptance Criteria Quality
   - Scenario Coverage
   - Edge Case Coverage
   - Non-Functional Requirements
   - Dependencies & Assumptions
   - Ambiguities & Conflicts
5. **Item Format**:
   ```
   - [ ] CHK### <Question about requirement quality> [Dimension, Spec §X.Y or Gap]
   ```
   - Question format asking about requirement quality
   - Quality dimension in brackets
   - Traceability reference to spec section or gap marker
6. **File Handling**:
   - New file: Start at CHK001
   - Existing file: Append from last CHK ID
   - Never delete or replace existing content

**Prohibited Patterns** (Testing Implementation):
- ❌ "Verify", "Test", "Confirm", "Check" + implementation behavior
- ❌ References to code execution, user actions, system behavior
- ❌ "Displays correctly", "works properly", "functions as expected"

**Required Patterns** (Testing Requirements Quality):
- ✅ "Are [requirement type] defined/specified/documented for [scenario]?"
- ✅ "Is [vague term] quantified/clarified with specific criteria?"
- ✅ "Are requirements consistent between [section A] and [section B]?"
- ✅ "Can [requirement] be objectively measured/verified?"

**Quality Gates**:
- ≥80% items include traceability references
- Items test requirements, not implementation
- Categories cover selected focus areas
- Format follows strict checklist template

**Extension Hooks**:
- `before_checklist`: Pre-checklist setup
- `after_checklist`: Post-checklist automation

---

### Phase 7: Implementation

**Command**: `/speckit.implement`

**Purpose**: Execute the implementation plan by processing all tasks in tasks.md.

**Inputs**:
- `tasks.md` from Phase 4
- `plan.md` from Phase 3
- Optional: `data-model.md`, `contracts/`, `research.md`, `quickstart.md`, constitution

**Outputs**:
- Implemented feature code
- Updated tasks.md with completed task checkmarks
- Implementation progress report

**Key Activities**:
1. **Check Prerequisites**: Verify FEATURE_DIR and tasks.md exist
2. **Check Checklist Status** (if checklists/ exists):
   - Scan all checklist files
   - Count total, completed, incomplete items
   - Display status table
   - **If any incomplete**: STOP and ask user to proceed anyway
   - **If all complete**: Automatically proceed
3. **Load Implementation Context**:
   - REQUIRED: tasks.md, plan.md
   - IF EXISTS: data-model.md, contracts/, research.md, constitution, quickstart.md
4. **Project Setup Verification**:
   - Detect project type (git, Docker, ESLint, Prettier, etc.)
   - Create/verify ignore files (.gitignore, .dockerignore, .eslintignore, etc.)
   - Append missing critical patterns if files exist
   - Create with full pattern set if files missing
5. **Parse Tasks**:
   - Extract phases: Setup, Tests, Core, Integration, Polish
   - Identify dependencies: Sequential vs parallel [P]
   - Extract task details: ID, description, file paths
6. **Execute Implementation**:
   - **Phase-by-phase**: Complete each phase before next
   - **Respect dependencies**: Sequential in order, parallel [P] together
   - **TDD approach**: Tests before implementation (if requested)
   - **File coordination**: Same-file tasks run sequentially
   - **Validation checkpoints**: Verify phase completion
7. **Implementation Order**:
   - Setup first: Project structure, dependencies, configuration
   - Tests before code: Contract tests, entity tests, integration tests
   - Core development: Models, services, CLI commands, endpoints
   - Integration: Database connections, middleware, logging, external services
   - Polish and validation: Unit tests, performance optimization, documentation
8. **Progress Tracking**:
   - Report progress after each task
   - Halt on non-parallel task failure
   - Continue with successful parallel tasks, report failed ones
   - Mark completed tasks as [X] in tasks.md
9. **Completion Validation**:
   - Verify all required tasks completed
   - Check implementation matches specification
   - Validate tests pass and coverage meets requirements
   - Confirm implementation follows technical plan
   - Report final status with summary

**Error Handling**:
- Halt execution on non-parallel task failure
- Provide clear error messages with context
- Suggest next steps if implementation cannot proceed
- For parallel tasks, continue with successful ones, report failures

**Quality Gates**:
- All checklists complete (or user explicitly proceeds)
- All required tasks completed
- Implementation matches specification
- Tests pass and coverage meets requirements
- Follows technical plan

**Extension Hooks**:
- `before_implement`: Pre-implementation setup
- `after_implement`: Post-implementation automation

### Phase 8: Convert Tasks to GitHub Issues (Optional)

**Command**: `/speckit.taskstoissues`

**Purpose**: Convert tasks.md tasks into GitHub issues for team tracking.

**Inputs**:
- `tasks.md` from Phase 4
- Git remote URL (must be GitHub)

**Outputs**:
- GitHub issues created in repository
- Issue IDs linked back to tasks

**Key Activities**:
1. **Verify Prerequisites**: FEATURE_DIR and tasks.md exist
2. **Get Git Remote**: `git config --get remote.origin.url`
3. **Validate GitHub URL**:
   - ONLY proceed if remote is a GitHub URL
   - NEVER create issues in repositories that don't match remote
4. **Create Issues**:
   - For each task in tasks.md
   - Use GitHub MCP server to create issue
   - Issue content representative of task

**Safety Constraints**:
- CRITICAL: Only create issues in repository matching git remote
- NEVER create issues in unrelated repositories

**Extension Hooks**:
- `before_taskstoissues`: Pre-conversion setup
- `after_taskstoissues`: Post-conversion automation

## Git Extension Commands

### `/speckit.git.initialize`

**Purpose**: Initialize a Git repository with an initial commit.

**When to Use**: Once at project start.

**Outputs**:
- Initialized Git repository
- Initial commit with message "Initial commit from Specify template"

**Customization**:
- Custom `.gitignore` templates
- Default branch naming
- Git LFS setup
- Git hooks installation
- Commit signing configuration
- Git Flow initialization

**Graceful Degradation**:
- If Git not installed: Warn, skip, project continues without Git
- If git init/add/commit fails: Surface error, stop command

---

### `/speckit.git.feature`

**Purpose**: Create and switch to a feature branch with sequential or timestamp numbering.

**When to Use**: Before `/speckit.specify` to create feature branch.

**Branch Numbering Modes**:
- **Sequential** (default): `NNN-short-name` (e.g., `003-user-auth`)
- **Timestamp**: `YYYYMMDD-HHMMSS-short-name` (e.g., `20260319-143022-user-auth`)

**Configuration**:
- Check `.specify/extensions/git/git-config.yml` for `branch_numbering`
- Check `.specify/init-options.json` for `branch_numbering` (backward compatibility)
- Default to `sequential` if neither exists

**User Override**:
- If `GIT_BRANCH_NAME` explicitly provided, use exact value (bypasses all prefix/suffix generation)

**Outputs**:
- JSON with `BRANCH_NAME` and `FEATURE_NUM`
- Branch created and checked out

**Graceful Degradation**:
- If Git not installed or not a repo: Warn, skip, output JSON with generated names

---

### `/speckit.git.commit`

**Purpose**: Auto-commit changes after a Spec Kit command completes.

**When to Use**: As a hook after/before core commands.

**Configuration** (`.specify/extensions/git/git-config.yml`):
```yaml
auto_commit:
  default: false          # Global toggle
  after_specify:
    enabled: true
    message: "[Spec Kit] Add specification"
  after_plan:
    enabled: false
    message: "[Spec Kit] Add implementation plan"
```

**Behavior**:
1. Determine event name from hook context (e.g., `after_specify`, `before_plan`)
2. Check config for `auto_commit.<event_name>.enabled`
3. Fall back to `auto_commit.default` if no event-specific key
4. Use per-command `message` if configured, otherwise default
5. If enabled and uncommitted changes exist: `git add .` + `git commit`

**Graceful Degradation**:
- If Git not available or not a repo: Warn, skip
- If no config file: Skip (disabled by default)
- If no changes to commit: Skip with message

---

### `/speckit.git.remote`

**Purpose**: Detect Git remote URL for GitHub integration.

**When to Use**: Before `/speckit.taskstoissues` or when GitHub integration needed.

**Outputs**:
- Repository owner (e.g., `github`)
- Repository name (e.g., `spec-kit`)
- Is GitHub: boolean

**Supported URL Formats**:
- HTTPS: `https://github.com/<owner>/<repo>.git`
- SSH: `git@github.com:<owner>/<repo>.git`

**Safety**:
- ONLY report GitHub repository if remote URL points to github.com
- Do NOT assume remote is GitHub if URL format doesn't match

**Graceful Degradation**:
- If Git not installed, not a repo, or no remote configured: Return empty, do NOT error

---

### `/speckit.git.validate`

**Purpose**: Validate current branch follows feature branch naming conventions.

**When to Use**: Anytime to verify branch naming compliance.

**Validation Rules**:
- **Sequential**: `^[0-9]{3,}-` (e.g., `001-feature-name`)
- **Timestamp**: `^[0-9]{8}-[0-9]{6}-` (e.g., `20260319-143022-feature-name`)

**Outputs**:
- If on feature branch: `✓ On feature branch: <branch-name>`
- If spec directory exists: `✓ Spec directory found: <path>`
- If spec directory missing: `⚠ No spec directory found for prefix <prefix>`
- If not on feature branch: `✗ Not on a feature branch` with naming guidance

**Fallback**:
- If Git not available: Check `SPECIFY_FEATURE` environment variable
- If not set: Skip validation with warning

## Extension Hooks System

Speckit supports extension hooks that run before or after core commands. Hooks are configured in `.specify/extensions.yml`.

### Hook Configuration

```yaml
hooks:
  before_specify:
    - extension: git
      command: speckit.git.feature
      description: Create feature branch
      prompt: Create a feature branch for the specification
      optional: false
      enabled: true
      condition: "git rev-parse --is-inside-work-tree"
  
  after_specify:
    - extension: git
      command: speckit.git.commit
      description: Auto-commit specification
      prompt: Commit the specification changes
      optional: true
      enabled: true
```

### Hook Types

**Mandatory Hooks** (`optional: false`):
- Execute automatically
- Display: "Automatic Pre-Hook/Hook: {extension}"
- Wait for result before proceeding

**Optional Hooks** (`optional: true`):
- User can choose to execute
- Display: "Optional Pre-Hook/Hook: {extension}"
- Show command and prompt for manual execution

### Hook Filtering

1. Filter out hooks where `enabled: false`
2. Hooks without `enabled` field are enabled by default
3. Do NOT interpret or evaluate `condition` expressions
4. If no `condition` field or null/empty: treat as executable
5. If `condition` present: skip and leave evaluation to HookExecutor

### Hook Events

| Event | When | Typical Use |
|-------|------|-------------|
| `before_specify` | Before spec creation | Branch creation, setup |
| `after_specify` | After spec creation | Auto-commit, notifications |
| `before_plan` | Before planning | Context loading |
| `after_plan` | After planning | Auto-commit, sync |
| `before_clarify` | Before clarification | Spec loading |
| `after_clarify` | After clarification | Auto-commit |
| `before_tasks` | Before task generation | Context loading |
| `after_tasks` | After task generation | Auto-commit, sync |
| `before_analyze` | Before analysis | Artifact loading |
| `after_analyze` | After analysis | Report generation |
| `before_checklist` | Before checklist | Context loading |
| `after_checklist` | After checklist | Auto-commit |
| `before_implement` | Before implementation | Prerequisites check |
| `after_implement` | After implementation | Auto-commit, deployment |
| `before_constitution` | Before constitution update | Template loading |
| `after_constitution` | After constitution update | Template sync, auto-commit |
| `before_taskstoissues` | Before task-to-issues | Remote validation |
| `after_taskstoissues` | After task-to-issues | Notifications |

## Command Execution Flow (Typical)

### Scenario 1: New Feature from Scratch

```bash
# 1. Initialize project (one time)
/speckit.git.initialize

# 2. Create constitution (optional, one time)
/speckit.constitution "Our project values: test-driven development, user-first design, performance"

# 3. Start feature workflow
/speckit.specify "Add user authentication with OAuth2 and email/password login"
# → Creates: specs/001-user-auth/spec.md
# → Creates: specs/001-user-auth/checklists/requirements.md
# → (Git extension creates branch: 001-user-auth)

# 4. Clarify requirements (recommended)
/speckit.clarify
# → Resolves ambiguities in spec
# → Updates: specs/001-user-auth/spec.md

# 5. Create technical plan
/speckit.plan
# → Creates: specs/001-user-auth/plan.md
# → Creates: specs/001-user-auth/research.md
# → Creates: specs/001-user-auth/data-model.md
# → Creates: specs/001-user-auth/contracts/

# 6. Generate tasks
/speckit.tasks
# → Creates: specs/001-user-auth/tasks.md

# 7. Analyze consistency (optional)
/speckit.analyze
# → Produces analysis report (no file changes)

# 8. Generate quality checklists (optional)
/speckit.checklist "security"
/speckit.checklist "ux"
# → Creates: specs/001-user-auth/checklists/security.md
# → Creates: specs/001-user-auth/checklists/ux.md

# 9. Implement
/speckit.implement
# → Executes tasks.md
# → Updates: tasks.md with [X] checkmarks
# → Creates: implementation code

# 10. Convert to GitHub issues (optional)
/speckit.taskstoissues
# → Creates GitHub issues from tasks
```

### Scenario 2: Quick Feature (Skip Clarification and Analysis)

```bash
/speckit.specify "Fix typo in login error message"
/speckit.plan
/speckit.tasks
/speckit.implement
```

### Scenario 3: Complex Feature with Full Rigor

```bash

/speckit.specify "Implement end-to-end encrypted messaging system"
/speckit.clarify  # Resolve encryption algorithm, key management, etc.

```

## Key Design Principles

### 1. Separation of Concerns

- **Specification** (WHAT and WHY): Business value, user needs, success criteria
- **Planning** (HOW): Technical approach, architecture, data model, contracts
- **Tasks** (WHEN and WHO): Execution order, dependencies, parallel opportunities
- **Implementation** (DO): Code execution following tasks

### 2. Quality Gates at Each Phase

Each phase has explicit quality gates that must pass before proceeding:
- Spec: All requirements testable, no ambiguities, success criteria measurable
- Plan: All NEEDS CLARIFICATION resolved, constitution compliant
- Tasks: All tasks follow format, each story independently testable
- Implementation: All checklists complete, all tasks executed, tests pass

### 3. Extension Hooks for Customization

- Core workflows are stable and predictable
- Extensions add project-specific behavior via hooks
- Hooks can be mandatory or optional
- Conditions evaluated by HookExecutor, not workflow engine

### 4. Graceful Degradation

- Git not installed? Continue without Git features
- Missing optional documents? Generate from available context
- Hook fails? Surface error, allow user to decide next steps
- Checklist incomplete? Warn user, ask for explicit proceed decision

### 5. Token Efficiency

- Progressive disclosure: Load only necessary context
- Limit clarifications: Max 3 in specify, max 5 in clarify
- Limit findings: Max 50 in analyze, summarize overflow
- Deterministic results: Rerunning produces consistent output

## Common Pitfalls and Best Practices

### Pitfalls to Avoid

1. **Skipping Clarification**: Increases downstream rework risk. Only skip for exploratory spikes.
2. **Implementation Details in Spec**: Spec should be technology-agnostic. Save tech decisions for plan.
3. **Too Many Clarifications**: Limit to 3 in specify, 5 in clarify. Prioritize by impact.
4. **Ignoring Constitution**: Constitution violations are CRITICAL. Resolve before proceeding.
5. **Incomplete Checklists**: If checklists exist, they must be complete before implementation.
6. **Task Format Violations**: All tasks must follow strict checklist format for consistency.
7. **Skipping Analysis**: For complex features, analysis catches costly inconsistencies early.

### Best Practices

1. **Always Run Clarify**: Even for simple features, clarify catches ambiguities early.
2. **Use Checklists Strategically**: Generate checklists for high-risk domains (security, performance, UX).
3. **Run Analysis for Complex Features**: Catches inconsistencies before implementation begins.
4. **Keep Specs Technology-Agnostic**: Focus on WHAT and WHY, not HOW.
5. **Make Success Criteria Measurable**: Include specific metrics (time, percentage, count, rate).
6. **Organize Tasks by User Story**: Enables independent implementation and testing.
7. **Use Git Extension**: Branch naming, auto-commit, and validation improve traceability.

## Troubleshooting

### "No feature description provided" Error

**Cause**: Empty command or missing user input.
**Solution**: Provide feature description: `/speckit.specify "Add user authentication"`

### "Cannot determine user scenarios" Error

**Cause**: Feature description lacks clear user flow.
**Solution**: Rewrite description with user perspective: "As a user, I want to..."

### Gate Failure: Constitution Violations

**Cause**: Plan conflicts with constitution principles.
**Solution**: Justify violation in plan or update constitution first.

### Checklist Incomplete Before Implementation

**Cause**: Checklists in `checklists/` directory have incomplete items.
**Solution**: Complete checklists or explicitly proceed with user confirmation.

### Missing Prerequisites Error

**Cause**: Required files (spec.md, plan.md, tasks.md) not found.
**Solution**: Run prerequisite commands in order: specify → plan → tasks → implement.

### Git Remote Not GitHub

**Cause**: `/speckit.taskstoissues` requires GitHub remote.
**Solution**: Configure GitHub remote or skip task-to-issues conversion.
